# F1 PITWALL – F1 통합 정보 웹사이트

웹프로그래밍 수업 텀프로젝트 (1인 개발). Formula 1 정보를 한 곳에서 통합 제공하는 웹 플랫폼.
GitHub: https://github.com/gksruf22/F1-pitwall

## 프로젝트 핵심 원칙

1. **통합 정보 제공**이 큰 틀이다. 기본 정보 · 실시간 · 분석 · AI · 커뮤니티가 **같은 정규화 데이터와 이벤트 저장소를 공유**한다. 기능마다 데이터를 따로 가져오지 않는다.
2. 화면(클라이언트)은 외부 F1 API를 **직접 호출하지 않는다.** 항상 자체 Express API만 호출한다.
3. 수업 기본 기술은 **HTML / CSS / JavaScript**, 활용 기술은 **DOM / WebAPI / Cloud / Server / AI**다. 이 기술들을 직접 구현해서 보여주는 것이 목적이므로 **프런트엔드 프레임워크(React, Vue 등)와 CSS 프레임워크는 쓰지 않는다.**
4. 핵심 기능은 실제 데이터로 구현하고, 라이브 기능은 **과거 레이스 시뮬레이션 모드**로 시연한다.
5. 계획서에 적은 기능이 기준이다. 기능을 임의로 추가·삭제하지 말고, 바꿀 필요가 있으면 먼저 알려 달라.

페이지 목록과 화면 구성은 `docs/sitemap.md`를 따른다.

### 신규 항목의 데이터 메모

- 요약 카드·순위 변동·격차: Jolpica 결과·순위 데이터로 계산한다(Event Processor가 아니라 API 계층에서 집계해 캐싱).
- 피트스톱 통계·일관성·Track DNA: 사전 수집한 레이스의 랩·피트·스틴트(·위치) 데이터로 계산한다. 수집하지 않은 레이스는 "데이터 없음"으로 표시한다.
- 드라이버 비교(헤드투헤드)의 예선 랩 격차·팀 폴 대비 격차는 레이스 랩뿐 아니라 **퀄리파잉 세션의 랩 데이터(OpenF1)도 함께 수집**해야 계산 가능하다 — 수집 스크립트 범위에 퀄리파잉 세션을 포함한다.
- 스피드트랩(구간 최고속도)은 OpenF1 `car_data` 텔레메트리에서 뽑아내야 하는데, 실제로 트랙별 스피드트랩 지점 데이터가 응답에 있는지 구현 전에 직접 호출해 확인한다 — 없으면 이 항목은 생략한다.
- 하이라이트 피드: 결과 데이터에서 규칙 기반으로 항목을 먼저 만들고(예: 폴 포지션 횟수, 연속 포디움), AI는 문장 다듬기에만 쓴다. 숫자는 AI가 만들지 않는다.
- 참고 사이트(app.formula1dashboard.com)는 기능 아이디어만 참고한다. 화면·문구·코드는 따라 하지 않는다.

## 개발 단계와 우선순위

- **1단계 (1~3주차)**: 데이터 수집·정규화, Event Processor·Cache, REST API, 기본 정보 페이지(요약 카드·순위 변동 포함), 시각화, Strategy Analytics(피트스톱 통계·일관성 포함), SSE + Live Race Control(시뮬레이션)
- **2단계 (4~5주차)**: Replay Engine(Canvas), Firebase 인증, AI Race Engineer, 하이라이트 피드, Track DNA, Fantasy F1(자동 채점), 앱 내 알림
- **3단계 (6주차)**: Web Push·PWA, 커뮤니티·관리자, Changelog, 통합 테스트, 배포

앞 단계가 끝나기 전에 뒤 단계 기능을 시작하지 않는다. 단계 안에서도 "데이터 → API → 화면" 순서로 만든다.

## 아키텍처

```
Client (Vanilla JS SPA)  ── Dashboard · Live · Replay · Strategy · AI · Community
        │  REST / SSE
Express API Server       ── REST · SSE Gateway · Search · AI Service · Auth Middleware
        │                    · Prediction Engine · Notification Service
Data Processing Layer    ── API Collector → Data Normalizer → Event Processor → Cache Manager
        │
Firebase (Auth · Firestore · Storage)      External: Jolpica F1 · OpenF1 · LLM API
```

- 정적 화면은 Vercel, SSE를 유지하는 Express 서버는 **별도 서버**로 분리한다(서버리스는 연결 유지형 SSE에 부적합).
- Redis는 쓰지 않는다. 메모리 캐시 + Firestore/파일 캐시로 충분하다.

## 공통 이벤트 모델

라이브·리플레이·AI 분석이 모두 이 형식의 이벤트를 소비한다.

```js
{ sessionKey, ts, lap, type, driver, data }
// type: GREEN_FLAG | SAFETY_CAR | RED_FLAG | PIT_IN | PIT_OUT | FASTEST_LAP | POSITION_CHANGE
```

- 이벤트는 수집된 원본(레이스 컨트롤 메시지, 피트·스틴트, 랩, 순위 기록)에서 **Event Processor가 생성**하고, 저장한 뒤 모든 기능이 재사용한다.
- 시뮬레이션 모드: 저장된 이벤트·순위 스냅샷을 시간 순서대로 SSE로 흘려보낸다(배속 지원).

## 데이터 소스와 제약

- **Jolpica F1** (일정·결과·순위·역대 기록): 익명 기준 초당 4회 / 시간당 500회 수준 → 반드시 캐싱.
- **OpenF1** (세션·드라이버·랩·피트·스틴트·순위·위치·레이스 컨트롤): 2023년 이후 과거 데이터는 무료, 분당 30회·초당 3회 제한. **세션 중 실시간 접근은 유료**이므로 기본은 시뮬레이션 모드. 위치·텔레메트리 응답이 매우 크다.
- 따라서 **수집 스크립트(`scripts/collect`)로 레이스 3~5개를 미리 내려받아 정규화·가공(샘플 간격 축소)해 저장**하고, 서버는 저장본을 제공한다. 수집 시 호출 한도를 지키는 대기(throttle)와 재시도를 넣는다.
- 엔드포인트·필드 이름은 구현 전에 실제 응답으로 확인한다(추측해서 작성하지 않는다).
- 무료 호스팅 서버는 유휴 시 꺼지고 로컬 파일이 사라질 수 있다. 영속 데이터는 Firestore나 저장소에 포함된 정적 JSON에 둔다. 발표 전 서버 기동을 확인한다.

## 기술 스택과 규칙

- **프런트엔드**: HTML5 시맨틱, CSS(변수 · Grid/Flexbox · 반응형, 다크/라이트), JavaScript ES 모듈. SPA는 History API로 직접 라우팅. 차트는 Chart.js, 서킷 맵은 SVG, 리플레이는 Canvas + `requestAnimationFrame`.
- **WebAPI 활용**: Fetch, EventSource(SSE), Canvas, History API, localStorage/IndexedDB, Service Worker, Notification/Push API, Intl(KST 변환).
- **서버**: Node.js + Express(ES 모듈). 응답은 JSON, 오류는 일관된 형식(`{ error: { code, message } }`).
- **클라우드**: Firebase Auth · Firestore · Storage, GitHub 연동 자동 배포.
- **AI**: LLM 호출은 **서버에서만** 한다. Function Calling으로 자체 API를 조회해 답하고, 답변에 **근거 데이터를 함께 표시**한다. 화면에 "AI 생성 내용" 문구를 둔다. 호출 횟수·입력 길이를 제한한다.
- 시간은 UTC로 저장하고 화면에서 KST로 변환한다.

### 코딩 규칙

- 의존성 추가는 먼저 이유를 설명하고 승인을 받는다. 작은 기능은 라이브러리 없이 직접 구현한다.
- 코드의 식별자·주석 규칙: 식별자는 영어, 주석과 UI 문구는 한국어.
- 파일 하나는 하나의 책임. 공통 모듈(router, store, api client, UI 컴포넌트)을 먼저 만들고 재사용한다.
- 사용자 입력과 외부 데이터를 DOM에 넣을 때는 `textContent` 또는 이스케이프를 사용한다(`innerHTML`에 그대로 넣지 않는다).
- 비동기 요청에는 로딩 상태와 오류 화면을 항상 둔다.

### 보안

- API 키·서비스 계정 등 비밀 값은 코드·로그·커밋에 넣지 않는다. `.env`를 쓰고 `.env.example`만 커밋한다. `.gitignore`를 먼저 설정한다.
- Firestore 보안 규칙: 작성자만 수정·삭제, 관리자 권한은 서버에서 검증한다.
- 이미지 업로드는 형식·용량을 검사한다.

### 저작권

- F1 공식 로고·사진·폰트는 사용하지 않는다. 직접 만든 디자인을 쓰고, 화면 하단에 **비공식 팬 프로젝트**임을 명시한다.

## 권장 디렉터리 구조

```
client/          # 정적 SPA (index.html, css/, js/{router,store,api,components,pages})
server/          # Express (routes/, services/{ai,prediction,notify}, sse/, middleware/)
pipeline/        # collector, normalizer, event-processor, cache
scripts/         # 데이터 수집·가공 스크립트
data/            # 사전 수집·가공한 레이스 데이터(JSON) — 용량 큰 원본은 커밋 금지
docs/            # 기능 명세, 설계, weekly/ 주차 보고서
```

## 작업 방식 (Claude에게)

- 한 번에 한 기능만 작업한다. 작업 전에 계획을 3~5줄로 알려 주고, 끝나면 **실행해서 동작을 확인**한 뒤 결과를 요약한다.
- 불확실한 API 응답·필드는 실제로 호출해 확인한다. 확인하지 않고 지어내지 않는다.
- 새 기능을 만들 때 관련 문서(`docs/`)를 같이 갱신한다. 주차 말에는 `docs/weekly/YYYY-WW.md`에 한 일·문제·다음 계획을 정리하도록 도와 달라.
- 커밋은 기능 단위로 작고 자주, 메시지는 `feat: …`, `fix: …`, `docs: …` 형식으로 한다.
- 범위가 커 보이면 줄이자고 제안하기 전에, 먼저 **공통 구조로 재사용할 방법**이 있는지 찾는다.
